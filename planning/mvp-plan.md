# MVP Plan

## Strategy: Convention First, Code Second

The magic moment isn't when the CLI works — it's when you open any AI coding assistant in a Flutter project, type *"extract all strings on this screen to translations and translate to Spanish"*, and the AI does it perfectly because `dialect.yaml` teaches it the convention.

**If you can record a 2-minute demo of that workflow and post it to Flutter Reddit / Twitter, you'll know within 48 hours if people care.** If they do, build the CLI. If they don't, you saved yourself months.

---

## First Move: Prove the Convention

1. Create a sample Flutter app with 2-3 screens and hardcoded strings.
2. Run `dialect init` to scaffold the `dialect/` directory with a convention-documented `dialect.yaml`.
3. Test it: point any AI assistant at `dialect.yaml` — can it reliably extract, key, and translate strings following the convention?
4. Record the demo.

The CLI can wait. The convention can't.

---

## Platform Priority

Focus on platforms where Dialect adds the most value: native mobile apps and their backends. Nobody else syncs ARB, `.strings`, `strings.xml`, and backend JSON from one canonical source.

| Priority | Platform | Why |
|---|---|---|
| Primary | **Flutter** | Home audience. ARB is the native format — adapter is a file copy. Full OTA via `dialect_ota`. |
| Primary | **iOS (Swift)** | Terrible localization DX. `.strings`/`.stringsdict` format sync is high value. No OTA needed — translations ship with binary. |
| Primary | **Android (Kotlin)** | Same story. `strings.xml`/`plurals.xml` format sync. No OTA needed. |
| Primary | **Backend (Node, Python, C#, Go)** | Flat JSON or ICU JSON. Shared strings with mobile. The cross-platform sync story is the strongest pitch. |
| Secondary | **React Native** | Supported via i18next-json adapter. RN teams already have decent tooling with i18next. |
| Secondary | **React Web** | Same adapter as RN. Supported as output, not the target audience. |

**The rule:** Flutter first, then iOS + Android + backend together (the core sync story), then React/RN adapter for teams that also have JS apps.

See [Frontend Platforms](../docs/platforms-frontend.md) and [Backend Platforms](../docs/platforms-backend.md) for full integration details.

## v1 — Open-Source Tooling

Ship a complete, free, open-source localization toolkit. Prove the thesis, build community, establish the standard.

### v1.0 — Foundation

The spec, the validation, the AI integration, and the dashboard. Flutter-only.

**Convention and config:**

- File structure convention as clear documentation.
- ARB-as-canonical-source pattern defined.
- Example `dialect.yaml` and `glossary.yaml`.
- Sample Flutter project with the structure in place.
- **Stable `icu-json` and `flat-json` output spec** in `dialect/spec/icu-json.md` and `dialect/spec/flat-json.md`. Versioned contract so backend localizer snippets/packages don't drift as Dialect evolves.

**Commands:**

- `dialect init` — scaffold the `dialect/` directory.
- `dialect status` — coverage overview table.
- `dialect import` — **AI-pointer flow.** Writes `.dialect/import-plan.md` with structured instructions for the user's AI agent (Cursor / Claude Code / Cline / Copilot / etc.) to read existing ARB files, rename keys to `namespace.camelCase`, backfill `@description` from callsite context, and produce canonical ARB in `dialect/source/`. Dialect itself never parses source code or alternative formats — the user's AI does.
- `dialect describe` — **AI-pointer flow.** Writes an instruction file telling the user's AI to scan callsites and fill missing `@description` fields. Multiplies quality of every downstream operation that consumes `@description` (translation, glossary matching, review UI context).
- Flutter adapter (ARB-to-ARB).
- `dialect.yaml` generated by `dialect init` with convention header comments that teach any AI assistant the Dialect standard (editor-agnostic — works with Cursor, Copilot, Windsurf, Claude Code, Cline, Aider, and anything else that reads files).

**`dialect check` (expanded scope):**

Structural validation (existing): every source key exists in all target locales; placeholder variables match; ICU plural categories are valid; no empty values.

**New semantic heuristics** — deterministic, no AI required. These catch the most common `dialect translate` failure modes:

- **Source-equality.** Flag any translation whose value equals the source value (silent passthrough — the most frequent LLM translation failure).
- **Length ratio.** Flag translations outside `[0.3×, 2.5×]` of source length. Configurable per-locale via `dialect.yaml` (German runs long, Japanese short). Warning, not error.
- **Untranslated English fragments.** Regex for English-looking word sequences in non-English locale files.
- **Glossary enforcement.** For every glossary term that appears in a source string, check that the corresponding translation contains the prescribed term. `@key.glossary_exempt: true` escape hatch for non-literal usage.

Soft-mode by default on fresh imports (warnings + helpful hints); `--strict` for CI promotes all warnings to errors. This makes the glossary load-bearing instead of decorative.

**Dashboard (`dialect serve`):**

Local web UI for non-developer review and editing. Moved up from v1.3 because the dashboard *is* the visual "wow" of the demo — a Flutter dev showing translations sync across platforms with a live-editing UI is the screenshot that travels on Reddit/Twitter.

- Dart Shelf server on `localhost:4077`.
- Svelte SPA embedded as static assets in the CLI binary (no `npm install`, no build step for end users).
- REST API backed by the local `dialect/` directory.
- Translation table with source + target side-by-side.
- `@key` descriptions and glossary terms surfaced inline as translator context.
- Filters by missing translations, namespace, feature file. Search by key or string content.
- Inline editing with save-to-file.
- Pin/lock to mark translations as human-approved (prevents `dialect translate` from overwriting).

**OSS hygiene:**

- `LICENSE` (MIT), `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, issue/PR templates.

**Design principle that drives v1.0:** wherever Dialect does *semantic* work (importing, describing, translating, key renaming), it ships a structured instruction file and lets the user's AI execute. Dialect ships *syntactic* work itself (format conversion, validation, sorting). This keeps the codebase small, model-agnostic, and on-brand: we are the convention; the AI does the work.

### v1.1 — iOS + Android + Backend Sync

Cross-platform sync is the core value proposition. This is what nobody else does.

- iOS adapter (`.strings` + `.stringsdict`) — format sync, translations ship with the binary.
- Android adapter (`strings.xml` + `plurals.xml`) — format sync, translations ship with the binary.
- `dialect sync` with flat-json adapter for backends (strip metadata, flatten ICU to simple interpolation).
- `dialect sync` with icu-json adapter for backends needing full pluralization (strip metadata, preserve ICU expressions).
- **Per-stack backend integration docs with drop-in localizer templates** — Django (JSON catalog backend swap), Flask/FastAPI, Node, Go. Each template is lossless: callsites keep using the stack's native localization interface, only the backing store changes. See [Backend Humility](competitive-strategy.md#backend-humility) for the principle. This replaces shipping `.resx` / `.po` adapters.
- **`Dialect.AspNetCore` NuGet package** — first-class real package (not a copy-paste snippet) for ASP.NET. One-liner adoption:

  ```csharp
  // Program.cs
  builder.Services.AddDialectLocalization("wwwroot/locales");
  ```

  Wraps the `JsonStringLocalizer : IStringLocalizer<T>` implementation, ICU MessageFormat evaluation, and `Accept-Language` culture resolution. Callsites use unchanged `IStringLocalizer<T>`. This is the highest-leverage adoption artifact for the Flutter + ASP.NET segment — `dotnet add package Dialect.AspNetCore` is the install ergonomic BE engineers expect. The raw template stays documented as the underlying mechanism / fallback for teams that can't add a dependency. Other backend stacks stay as snippets until demand justifies separate packages.

- `dialect import` plan templates extended to cover ARBs from other Flutter projects with non-standard conventions.
- Split-file architecture support (`features/checkout_en.arb`, `features/settings_en.arb`).
- Namespace filtering (`common` + `mobile` to Flutter/iOS/Android, `common` + `backend` to backends).

### v1.2 — AI Translation + OTA + Merge Safety

For large projects where the AI assistant hits context limits, plus the delivery pipeline, plus production-team safety nets.

- `dialect translate` — **AI-pointer flow primary, built-in LLM call as convenience.**
  - Default: diff `en.arb` against target locale, write instructions to `.dialect/translate-plan.md` for the user's AI agent to execute. Same pattern as `dialect import` and `dialect describe`.
  - Convenience: `dialect translate --auto --provider {anthropic|openai}` calls the LLM directly for CI / scripting. The agent-pointer flow is the recommended path because it's model-agnostic, vendor-neutral, and doesn't go stale with model upgrades.
- `dialect publish --adapter local` — output versioned translation bundle to a folder for OTA.
- OTA manifest format (`dialect-manifest.json`).
- `dialect publish --adapter github` — commit to a release branch for Git-based OTA.
- **`dialect merge` + `.gitattributes` merge driver** — opt-in via `dialect init --enable-merge-driver` (or `dialect install-merge-driver` post-init). Key-aware JSON 3-way merge that handles parallel branches touching the same ARB file without dropping keys or mis-merging plurals. Standard `git` JSON merge is line-based and easy to resolve wrong; this makes ARB merges safe by default. Off by default in v1.0 — teams opt in when they grow into the problem.

### v1.3 — OTA Client

Ship the client-side OTA piece. (Review UI / dashboard already shipped in v1.0.)

- `dialect_ota` Flutter package — custom `LocalizationsDelegate` that checks a URL for newer translations.
- Caching, offline fallback, version checking.
- Dashboard enhancements built on the v1.0 `dialect serve` base: comment threads on individual strings, change history, search-and-replace across locales.

### v1.4 — React / React Native

Secondary platform support for teams that also ship a JS app alongside their Flutter / iOS / Android target.

- `dialect sync` with i18next adapter for React and React Native (ICU → i18next plurals, namespace → nested keys).
- `dialect publish --adapter http` — POST translation bundles to any backend endpoint.

**Note on `.resx` and gettext `.po`:** Not on the roadmap as adapters. ASP.NET and Django are covered by the lossless localizer-template path in v1.1 (icu-json + drop-in `JsonStringLocalizer` for ASP.NET, JSON catalog backend swap for Django). We don't ship lossy format adapters when a lossless template path exists — it would silently degrade ICU plurals and named placeholders. See [Backend Humility](competitive-strategy.md#backend-humility).

### v1.5 — Production Polish

Ship-quality release.

- Robust ICU MessageFormat parsing (nested plurals, select expressions, gender variants).
- Good error messages for every failure mode.
- Full documentation site.
- GitHub Action for `dialect check` in CI.
- `dialect diff --format markdown` for PR comments.
- Post on Flutter Reddit, dev.to, Hacker News.

## v2 — Business Layer

Only start v2 if v1 has real traction. The open-source toolkit must stand on its own first. v2 adds hosted services and premium features on top of the free foundation.

### Trigger: When to Start v2

Start when **at least 3 of these are true**:

- 1K+ GitHub stars
- 50+ teams confirmed using Dialect
- Unprompted inbound asking for hosted service
- Enterprise inquiry about self-hosted or SLA
- Competitor starts copying the convention (validation you're onto something)

### v2.0 — Dialect Cloud: Hosted OTA

The first monetization path. Managed translation hosting so teams don't self-host OTA.

- `dialect publish --adapter cloud` — push translations to Dialect's CDN.
- Dashboard for managing published versions, rollback, locale-level rollout.
- Pricing: free tier (1 project, 3 locales), paid tiers for teams.
- Edge-cached delivery via CDN.

### v2.1 — Hosted Review Dashboard

Take the `dialect serve` UI online so PMs and translators can review without running the CLI.

- Same SPA from v1.3, deployed as a hosted app.
- GitHub integration: connect a repo, auto-sync on push.
- Role-based access: reviewer, editor, admin.
- Comment threads on individual strings.
- Change history and audit log.

### v2.2 — CI Quality Gate

Premium translation quality scoring in CI pipelines.

- LLM-powered quality scoring per string (context match, tone, length constraints).
- GitHub Check integration: translations get a quality score in the PR.
- Threshold configuration: block merge below a quality score.

### v2.3 — Enterprise Features

For large orgs with compliance and scale needs.

- Translation memory across projects (reuse approved translations).
- Team glossary management (org-wide, project-level overrides).
- SSO / SAML integration.
- Usage analytics (which translations get overridden most, which locales lag).
- SLA support.

## Tech Stack

### CLI: Dart

- Flutter devs can contribute immediately — same language as their app code, same toolchain.
- ARB is Flutter's native format. Dart owns the ARB ecosystem (Flutter's own `gen_l10n` and `package:intl`). For ICU MessageFormat *parsing* the situation is messier: `package:intl_translation` has been deprecated and there is no well-maintained public Dart parser. Dialect therefore ships a focused ICU scanner in `lib/arb/icu_message.dart` — scope limited to placeholder-name and plural-category extraction (the two structural checks v1.0 needs). It does not evaluate or format messages. If a v1.1+ check rule needs deeper AST analysis (skeleton parsing, gender variants, etc.) we swap in a real parser at that point. Validated against five models in `example/_validation/COMPARISON.md`; full ICU edge-case coverage in `test/arb/icu_message_test.dart`.
- `dart compile exe` produces a fully self-contained ~6-8 MB native binary. No Dart runtime needed at runtime.
- Flutter devs install via `dart pub global activate dialect`. Backend engineers install pre-built binaries (Homebrew / Scoop / curl) and never see the Dart SDK. See [Distribution](#distribution) below.
- LLM client for `dialect translate --auto` is a hand-rolled HTTP wrapper around Anthropic / OpenAI REST APIs (~50 lines per provider). No community SDK dependency that could rot.

### Review UI: Svelte

- Smallest bundles in the framework space — critical because the SPA is embedded as static assets in the CLI binary.
- No virtual-DOM overhead for a table-heavy UI (translation grid, inline edits, filters).
- Built with Vite, output to `dist/`, embedded as Dart `assets/`. The CLI's Shelf server serves the SPA and a small REST API on `localhost:4077`.

### OTA Flutter Package: Dart

- Thin wrapper around `http` + `shared_preferences` + a custom `LocalizationsDelegate`.

### ASP.NET Integration: C#

- Lives in *user* projects, not the Dialect CLI codebase.
- Ships as a docs page with a copy-pasteable ~30-line `JsonStringLocalizer : IStringLocalizer<T>` template + DI registration snippet. See [docs/platforms-backend.md](../docs/platforms-backend.md).

### Future: Potential Go Rewrite for CLI

- Go is the industry default for OSS CLIs in 2026 (`gh`, `kubectl`, `terraform`, `hugo`, `fly`, `doctl`, `neonctl`, `lokalise-cli`). If Dialect grows beyond the Flutter audience and Dart's "Flutter-tool" signal becomes a perceived barrier for Node / Python / Go backend-led teams, port to Go.
- Cheaper to learn coming from C# / Dart than Rust. Same single-binary distribution story.
- Rust is parked further out — only justified if Dialect grows into performance-sensitive territory (large monorepo scans, editor-extension real-time validation).
- Only worth doing if there's real demand from non-Flutter users.

## Distribution

The distribution story is what makes Dialect feel like a real cross-platform tool to a backend engineer rather than "a Flutter thing." Commit to all of these from v1.0 launch — they're each ~half a day of setup.

| Channel | Audience | Mechanism |
|---|---|---|
| `dart pub global activate dialect` | Flutter devs | Pub package (free with Dart SDK) |
| `brew install yourname/tap/dialect` | macOS backend engineers | Homebrew tap with pre-built binary |
| `scoop install dialect` | Windows backend engineers | Scoop manifest |
| `curl -fsSL https://dialect.dev/install.sh \| sh` | Linux / CI / one-off | Shell installer pulling GitHub Release binary |
| `ghcr.io/yourname/dialect:latest` | CI pipelines | Docker image |
| `uses: yourname/dialect-action@v1` | GitHub Actions CI | Composite action wrapping the Docker image |

GitHub Actions builds the binaries for macOS (x64 + arm64), Linux (x64 + arm64), and Windows (x64) on every release tag via `dart compile exe`, uploads them to the GitHub Release, and updates the Homebrew tap / Scoop manifest automatically.

The result: a backend engineer's adoption path looks identical to installing `gh` or `kubectl` — they don't know or care what Dialect is written in.

## What External Reviews Flagged

Five external perspectives reviewed the Dialect design (see [`agents-reviews/`](../agents-reviews/)). Here's what we acted on and what we intentionally parked.

### Addressed in v1

- **License was TBD** (Contributor, Vercel) — Now MIT.
- **Key style ambiguity** (Contributor) — Clarified: `namespace.camelCase` with deterministic sorted output.
- **README presented planned features as ready** (Contributor) — Added status column to CLI command table.
- **No OSS onboarding scaffolding** (Contributor) — Added `LICENSE`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`.
- **Backend flat-json loses ICU safety** (Lokalise) — Added `icu-json` format option; teams choose per-service.
- **Must-buy vs nice-to-have tension in v2** (VC) — Acknowledged in business analysis; v2 pricing deferred until real demand signals.

### Intentionally Parked for v2

- **RBAC, audit trails, approval workflows** (Duolingo, Lokalise) — Already planned in v2.1 and v2.3.
- **Translation memory and vendor handoff** (Duolingo) — v2.3.
- **Confidence scoring / quality gates** (Duolingo, VC) — v2.2.
- **Tiered locale quality policies** (Duolingo) — Future `dialect check` flag.
- **SSO/SAML** (Lokalise, VC) — v2.3.

### Intentionally Skipped

- **"AI can't handle regulated/legal content"** — The lock/pin mechanism and `dialect serve` review UI exist for this. Human override is the answer, not a compliance workflow engine.
- **"No dashboard scales indefinitely"** — Correct; v2 hosted dashboard is the answer. v1 local UI is scoped for small-to-mid teams.
- **"Core value is replicable / thin moat"** — True of any OSS convention project. The moat is community adoption, not code.
